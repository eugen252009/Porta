# Session workspaces and Git projects

Porta creates a server-owned workspace for every local conversation session. Filesystem, command, and Git tool providers resolve the workspace from the tool context's session ID on every invocation; they do not accept a model-selected workspace root. Workspaces are stored as UUID-named directories under `$PORTA_DATA_DIR/workspaces` (default: `.porta/workspaces`) with a mode-0600 atomic registry beside them. The workspace parent and per-workspace directories are mode 0700. Workspace IDs and absolute paths are not needed by the model.

New sessions start with an empty directory unless the user explicitly selects a saved project or supplies a Git remote to clone. The existing `filesystem.root` remains required to enable filesystem tools and continues to serve existing base-workspace/persistence integrations; it is not copied into new session folders. Existing workspaces are not migrated automatically. On first resume of a legacy session, Porta provisions a new empty session workspace; the old configured-root files remain untouched and can be cloned or imported deliberately.

## Clone on session creation

The local Web UI's **New chat** form accepts a repository remote, an optional saved project, and explicitly assigned Git credentials. A clone completes before the session is created. Failed or cancelled setup removes the staging directory and does not leave an active session workspace. Clone uses direct argv (never a shell), a server-generated destination, a ten-minute deadline, bounded process output, disabled terminal prompts, disabled system/global Git configuration, disabled hooks, and no recursive submodule initialization. Git's `ext` remote helper and unknown transport helpers are denied. Standard HTTPS/HTTP, SSH/SCP-style remotes, `git://`, and local/file remotes are supported when the installed Git supports them. Embedded URL credentials are rejected.

The transport is not restricted to a hard-coded provider list. HTTPS credentials are supplied through a temporary, private askpass helper that responds only to prompts for the assigned remote host. SSH private keys are copied to a mode-0600 temporary file and offered only for the selected remote host/alias. SSH runs with an isolated config, no inherited SSH agent or default user keys, and strict host-key checking. Credentialed SSH requires a user-supplied `known_hosts` file; without an assigned SSH key, only the server's `/etc/ssh/ssh_known_hosts` is trusted. Optional SSH config is limited to non-executable host mapping directives; `ProxyCommand`, `ProxyJump`, includes, forwarding, and custom identity/known-hosts overrides are rejected. Passphrase-protected SSH keys are not currently supported.

Repository credentials are never accepted in remote URLs, committed to `.git/config`, returned by credential APIs, or added to conversation/job history. Credential material is sent once to the authenticated Porta credential endpoint when a credential is created; repository/session requests carry only explicitly selected credential IDs. Secret inputs are cleared after submission, and the UI does not persist secret material in local storage or display it in responses. Porta stores credential files on the server in `$PORTA_DATA_DIR/git-credentials`, under mode-0700 directories and mode-0600 files. HTTPS askpass and SSH config/key material are written to a mode-0700 temporary directory and deleted after each clone/fetch/push attempt. Git global/system credential helpers, SSH agents, and default user SSH keys are not implicitly inherited. Global credentials are listed as metadata only and must be explicitly selected for a session; session credentials are bound to one session and removed when that session is deleted (including when its project is kept). Porta refuses to delete a global credential while any session workspace references it; remove the assignment/delete or detach the session first.

Credential files are plaintext at rest, protected by local filesystem permissions—not encrypted with a keychain. Anyone controlling the Porta service account or its data volume can read them. Use a dedicated private data volume, rotate/revoke credentials when appropriate, and expose this feature only to trusted authenticated users. The current WebAuthn UI is single-tenant: saved projects and global credentials are visible to any authenticated human principal on that Porta node. Per-user project/credential ownership is not implemented.

Cloning can access network hosts or local Git repositories that the Porta service account can access. There is no Git egress host allowlist, local-file source allowlist, clone-size quota, or disk quota yet; clone is bounded by a ten-minute deadline but a large repository can consume server disk. Do not expose clone/credential creation to untrusted users. `file://` is intentionally available for local repositories; it can read repositories accessible to the service account. Git transport helpers are intentionally disabled because they may execute arbitrary helper programs.

## Session Git tools and policy

Git tools operate only in the assigned session workspace. When Git is enabled and the executable is available, session Git tools are registered even if the configured base directory is not itself a Git repository; the session workspace may be cloned later during session provisioning. Local inspection includes status, branches, diff, show, and log. `git/fetch` updates remote refs; `git/commit` creates a local commit after its existing revision/conflict checks; `git/push` pushes the configured branch. Fetch/commit/push use only the assigned session/global credential selected for the remote transport. HTTPS askpass and SSH key delivery are host-scoped; a different remote host does not receive the selected secret. Remote credential operations require session context and fail closed otherwise. Git errors redact URLs containing user information and temporary credential paths.

Git commands remain subject to Porta's existing authorization policy. Under `require-approval`, they require approval. Under workspace authorization, Git/network tools remain approval-gated; only eligible ordinary filesystem operations are automatically allowed. No clone, fetch, commit, or push is inferred from an assistant message. Command execution is a separate capability and remains approval-gated; workspace authorization only registers it when the selected sandbox enforces its filesystem boundary. Host-process execution is not isolation.

The session directory confines Porta's filesystem and Git tool providers. It does not turn a shared host process into an OS security boundary: an explicitly approved command can have whatever host access its configured runtime/sandbox actually permits. Review command allowlists and sandbox capability reports accordingly.

## Keep, delete, reopen

Deleting a local session in the Web UI requires an explicit choice:

- **Keep as saved project** detaches its directory from the session and adds it to the saved-project list. No Git commit or push is performed.
- **Delete files** removes the workspace directory after validating it is a direct, non-symlink child of Porta's workspace root. The registry update uses an atomic tombstone/rename sequence.
- **Cancel** closes the dialog and performs no API request.

Saved projects can be reopened from **New chat**; Porta binds the existing directory to one new session at a time. Credential assignments are not carried over when a project is saved/reopened; explicitly select credentials again. Saved projects can also be permanently deleted from Settings after confirmation. API deletion requires `DELETE /api/sessions/:id` with JSON `{ "disposition": "keep" | "delete" }`; omission or any other value is rejected. `GET /api/projects` lists saved-project metadata, and `DELETE /api/projects/:workspaceId` deletes a saved project. Session workspace and credential APIs are local-node operations; remote/federated session workspace provisioning is not implemented.

These project/workspace APIs are separate from SQLite conversation persistence. Deleting a session closes its conversation and applies the chosen workspace disposition. Keeping a project does not preserve session history as a new session; reopening starts a new conversation over the retained files. Ordinary session close/terminal exit does not delete the workspace, so an explicitly resumed session keeps using its existing directory.

## Verification

`tests/session-workspaces.test.ts` covers per-session separation, atomic persistence, keep/reopen/delete, symlink replacement, clone argv/policy/deadline/cancellation/failure cleanup, credential file modes, explicit credential assignment, host-scoped askpass, strict SSH host verification, and temporary-secret cleanup. `tests/session-workspaces-web.test.ts` exercises authenticated clone/session creation, URL credential rejection, secret-free API responses, explicit deletion choices, saved-project reopening, and credential cleanup. The integrated E2E tests exercise filesystem/command/Git routing through a cloned local repository. Tests use local fixtures only; no test connects to a remote Git host. A disposable live NAS/SSH qualification is documented in [NAS Git qualification](NAS-GIT-QUALIFICATION.md).
